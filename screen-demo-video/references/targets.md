# 观看端预设：手机 vs PC

同一份录屏、同一套旁白与字幕，只改**运镜与标注密度**。开工前必须确认观看端；用户没说就问，也可以一次出两版（两份 plan + 两套段号，旁白/字幕/时间轴完全复用）。

## 为什么必须分

源素材是 PC 录屏（常见 4480×2520 或 3840×2160）。

- **手机**：屏幕小，全貌下文字只有几个像素，看不清 → 必须频繁下探到正在讲的那一行/那一个控件。
- **PC**：屏幕本来就大，全貌看得清 → 频繁下探+来回推拉会被读成"一直在晃"，而且观众失去了页面整体布局的参照，看不懂系统在讲什么。用户原话："局部放大太频，导致这个结果"。

## 观看端与交付矩阵

| 交付名 | 画幅 | 运镜预设 | 字幕 |
| --- | --- | --- | --- |
| `第N集-<主题>-PC版.mp4` | 2560×1440 横屏 | 见"pc" | 压在录制画面底部（画面内） |
| `第N集-<主题>-手机竖版.mp4` | **2160×3840 竖屏**（版式基准 1080×1920 × 画质倍率 Q=2） | 见"mobile" | **在录制画面之外的独立字幕带** |

手机默认竖版；手机横屏（2560×1440 + 画面内字幕）只在用户明确要"横屏手机版"时才出，它已被设计方否过一次（竖屏播放时上下黑边+字幕压在画面上→挤、看不清）。

## mobile 运镜（手机版=竖屏 9:16）

| 项 | 值 |
| --- | --- |
| maxZoom | 2.2 |
| 单镜头运镜次数 | 2–4 次，按旁白点位走（行驻式跟随） |
| 姿态间隔 | 可短至 3–5s |
| 下探倍率 | 1.6–2.2（表格行、按钮、输入框） |
| 标注密度 | 每个被点名的控件都给框/环，约 1 个 / 6–8s |
| 呼吸 breath | 0.012 |
| 建立镜头 | 可省（观众不需要全貌） |

**竖屏版不许靠加深倍率换清晰度**：`poseOf` 的区域夹紧只跟画幅宽高比有关，16:9 视口下横竖两版算出的 k 完全相同，所以横屏版调好的 region/maxK 可以原样复用。把 maxZoom 提到 2.6 只会让标注框超出视口（框本身宽度是按 2.2 取景校验的），清晰度反而靠"录制卡片尽量宽 + 字幕出画面"来解决。

## pc（桌面/投屏观看）

| 项 | 值 |
| --- | --- |
| maxZoom | 1.6（硬上限，别用 2.0+） |
| 单镜头运镜次数 | 1–2 次；**每个镜头开头先 1.5–2.5s 全貌**（region=整个内容区，k≈1.0–1.12） |
| 姿态间隔 | ≥ 6s；看完局部必须回到全貌再收尾 |
| 下探倍率 | 1.25–1.6，只下探到"块"级（一张卡片/一列表格），不到单行 |
| 标注密度 | ≤ 1 个 / 12s，只在旁白明确点名控件时给框；框停留 ≥ 2s，不同时叠两个 |
| 呼吸 breath | ≤ 0.008，或设 0 |
| 换页规则 | 一旦页面跳转/切 tab，下一个姿态必须是全貌，不能沿用局部坐标 |
| 换镜节奏 | 剪段可以更长（宁少切不碎切），让画面稳定 |

量化自查：pc 版里 `k > 1.5` 的成片时长占比应 ≤ 35%，且每 20s 至少出现一次 `k ≤ 1.15` 的全貌。
用 `scripts/camera-audit.mjs <工程>` 量（PREP 出完 `build/html/partN.html` 即可跑，不必等渲染）。第六集两版的实测参照：

| 版本 | 运镜次数/分钟 | 全貌 k≈1 占比 | k>1.5 占比 | 最深 k | 连续看不到全貌 | 标注出画 |
| --- | --- | --- | --- | --- | --- | --- |
| 手机竖版 1080×1920 | 9.2 | 7.7% | 61.9% | 2.20 | 25.0s | 0/23 |
| 手机版（横屏，旧） | 9.2 | 7.7% | 61.9% | 2.20 | 25.0s | 2/23（标注早于落幅，已在 plan 修正） |
| PC 版 | 5.2 | 38.3% | 1.7% | 1.60 | 17.0s | 0/16 |

竖版与横屏手机版的运镜数字**逐格相同**是设计如此（同一套 region/maxK + 同为 16:9 视口 → `poseOf` 算出的 k 曲线一致）；两版差别全在版式：竖版录屏只占 960×540 卡片、字幕/角标/关键词移出画面。成片音频与横屏版 PCM 逐字节相同（同一批 span 切片），所以音档验收可直接沿用。

用户"一直在晃、看不到整体布局"的反馈对应的就是第一行；两版并存时把这两组数字写进交付说明。

## 竖屏 9:16 版式（手机版默认，硬要求）

设计方口径：手机上默认竖屏；字幕不许压在录制画面上（会挤、看不清），竖屏字幕样式与 PC 不同；手机是全面屏，录制画面两边要留空间。落到合成里就是**一张竖屏卡片：录屏只是其中一个 16:9 区块，字幕、章节、关键词都在录屏画面之外的深色版面上**。

**版式基准 1080×1920，输出按画质倍率 `Q` 整体放大（默认 Q=2 → 2160×3840）**。下表所有数字都是基准值，实际像素 = 基准 × Q；`build.mjs` 里只改 `Q` 一处，`px()`/`VW`/`mk()`/`S`/`poseOf` 全部自动跟随。`SRC_W` 仍是录屏真实宽（如 4480）。

```
VW=960Q  VH=540Q  VX=60Q  VY=440Q   // 录制视口：16:9 卡片，两边各留 60Q
S = VW / SRC_W                      // 源像素 -> 视口像素（poseOf/mark 都用它）
COL=820Q 整屏居中                    // 卡片以下的文字列：正对画面中心，右边缘仍避开操作栏
```

### 为什么竖版必须 Q≥2（清晰度硬指标）

设计方实测反馈："1080×1920 的竖版在电脑上双击默认比例打开看不清字，体积只有原片的 1/3"。根因不是码率——竖版每个录制像素拿到的比特其实是横屏版的 2.3 倍——而是**几何**：视口宽度被舞台宽度钳死，1080 舞台里卡片只有 960 宽，4480 宽的录屏被压到 0.21 倍，16px 的界面文字只剩 3px。

| 版本 | 录屏显示比例 | 结果 |
| --- | --- | --- |
| 横屏手机版 2560×1440 | 2560/4480 = 0.57 | 文字可读 |
| 竖版 Q=1（960 卡片） | 0.21 | 1:1 打开糊成一片 |
| **竖版 Q=2（1920 卡片）** | **0.43** | **1:1 可读，缩略图仍可辨字** |

- 唯一有效的杠杆是放大舞台，**不要靠提高 `maxZoom` 换清晰度**（会把标注框推出视口，见 pitfalls）。
- 抖音上传后会下采样到 1080×1920，所以 Q=2 的收益体现在电脑/平板观看与文件质量上，手机上仍按 1080 宽显示。
- 成本参考（301s 全片实测）：Q=1 ≈ 18 分钟 / 65 MB；Q=2 ≈ 75 分钟 / 173 MB（视频码率 4.44 Mbps）。渲染前先看剩余磁盘，见 pitfalls 的 1 GB 闸门。

| 纵向分区（基准像素） | 位置 | 内容 |
| --- | --- | --- |
| 状态栏留白 | 0–200 | 空（系统时间/信号 + app 的返回箭头/搜索图标） |
| 品牌带 | 左 120 / 上 262 | 系列名一行 + 本集短标题一行 |
| 章节角标 | 左 120 / 上 366 | 章节 pill 放在录屏上方，不遮画面 |
| 录制视口 | 440–980 | 录屏 + 运镜 + 标注，圆角卡片带描边投影 |
| **字幕带** | 1008 起 | 字幕在这块深色区域里，**不在录屏画面内**；与关键词带同区（按时间互斥） |
| 底部留白 | 1400–1920 | 空（app 的标题/作者/进度条区） |

- **顶部文字不许贴左上角**（设计方："视频上方的文字太靠上、太靠左，往下、往右调整一些"）：品牌带与章节角标的左边界从视口左边再缩进 60（`HEAD_X = VX + 60`，即基准 120），品牌带 top 262、角标 top 366，角标下沿与录制卡片之间留 ≥30 基准 px；右边缘仍收在 950 以内。

- **字幕要贴着画面下方**（间距约 28px）且**整屏水平居中**：设计方对"字幕离视频太远""字幕不居中"都提过意见。
- **右侧安全区**：抖音类 app 的点赞/评论/收藏竖排在屏幕右侧约 12%（1080 舞台里 x>950）且从中下部开始。录制卡片在它上方（y≤980）可以满宽 960；卡片以下的所有文字/标签必须收在 x≤950 内。
- **字幕规格**（与 PC 不同，写在 plan 里）：**全片固定字号** `subtitleFixed 48`（× Q），宽度 `subtitleWidth 820`。设计方明确否决过"按行长缩字号"（"有的字号大有的字号小，要保持统一字号；文字长了可以换行，但是不能缩小字号"）——一行放不下就**按字宽贪心断行**折到最多 3 行（能贴着标点就贴标点），字号始终不变；底色用深色圆角块，位置在字幕带顶部而不是屏幕底部。**这条只管竖版**，PC 版仍是"一行优先、放不下缩到 `subtitleMin`、最多两行"。
- **运镜视口是卡片不是整屏**：`poseOf` 里的 W/H 换成 VW/VH，中心钳位、`x=(VW/2-cx)*k` 都在视口坐标系里算；`#cam` 必须放在 `overflow:hidden` 的视口容器内，否则放大后画面会糊到字幕带上。
- **标注几何**：`left/top` 仍用 `源坐标 × S`（相对视口），描边/光晕按视口比例缩（第六集竖版用 inset 5 / border 2 / ring 62）。
- **验收增量**：`mark-fit` / `mark-shots` 要按视口矩形判出画，量具跑竖版时必须传放大后的舞台：`STAGE_W=2160 STAGE_H=3840 BAND=120,880,1920,1080`（Q=1 时是 `1080 1920 60,440,960,540`），`ink-audit` 要跑到"视口空白 ≤0.45"（终端/登录页这类内容贴左上的屏最容易放大成一片黑），并抽查字幕带最右边缘 ≤ 950Q；快照必须目视确认录制卡片四周留白与字幕落点，不能只看 html。
- **交付前必须量化清晰度**：`ffprobe` 取 `width/height/bit_rate`，算"录屏显示比例 = 视口宽 / SRC_W"与"每录制像素比特 = 码率 × 时长 / (视口宽 × 视口高 × 总帧数)"，再和横屏手机版对照。竖版这两个值低于横屏版就是退化，要提 Q 而不是加 maxZoom 或码率。

清晰度对照（第六集 301s / 9039 帧实测）：横屏手机版 0.57 / 0.043 bit；竖版 Q=1 0.21 / 0.101 bit（画面糊，被退回）；竖版 Q=2 0.43 / 0.071 bit。

## 一次出两版（PC + 手机竖版）的标准做法

用户说「PC 和手机都要」时，**交付两个文件**：`第N集-<主题>-PC版.mp4`、`第N集-<主题>-手机竖版.mp4`。手机横屏版不再默认出（已被设计方否过）。

```
videos/<ep>-tour/       # 手机版分镜（密运镜：maxZoom 2.2、约 1 标注/6-8s）—— 分镜母版，可不出片
  build/plan.mjs          # 唯一一份需要逐镜头写坐标的 plan
videos/<ep>-vertical/   # 交付①：手机竖版
  build/plan.mjs          # import 上面那份，只覆盖 subtitleMax/Min/Width + shortTitle
  build/build.mjs         # 拷 assets/templates/vertical/build.mjs（内置 Q）
videos/<ep>-pc/         # 交付②：PC 版
  build/plan.mjs          # 独立一份：同一批 spans/时间轴，camera 按 pc 预设重挑（全貌优先、≤1.6）
  build/build.mjs         # 拷 assets/templates/landscape/build.mjs（与手机版同一份渲染器）
assets/  -> 三个工程软链共用录屏与 span 音频（partN.wav 各自重切；音频必须是真实切片，见 pitfalls）
```

- **顺序**：先把手机版分镜跑到验收通过（`ink-audit` / `mark-fit` / 接触表），再派生竖版（只改版式，坐标不动）与 PC 版（改运镜密度，坐标要重挑）。竖版复用手机版的 region/maxK 是安全的：16:9 视口下 `poseOf` 算出的 k 曲线相同。
- **两份交付各跑一遍验收**：`camera-audit` 与 `mark-fit` 分开量、分开写进交付说明；音频侧只要 span 切片同源，成片 PCM 哈希与手机版一致即可继承音档验收。
- **成本**：PC 版 2560×1440 约 25–30 分钟；竖版 Q=2 约 60–80 分钟且要留 ≥1.5GB 磁盘（见 pitfalls 的 1GB 闸门）。
